# Publishing the MediaBridge Cloud File Archive spec (v1.0)

I've been heads-down for a while on [MediaBridge](https://github.com/), my
self-hosted media cataloging and backup tool, and specifically on the part
that ships files off to Google Cloud Storage. That format finally settled
down enough that I'm comfortable calling it done, so I wrote it up as an
actual specification instead of just "whatever the code happens to do" —
and I'd like other people to poke holes in it before I treat it as stable.

**tl;dr: [read the spec](/cfa-spec.md).** This post is the informal tour —
what it is, why it looks the way it does, and where I think it's still
shaky. If you write backup tools, or you just like arguing about tar
overhead margins, I'd love your eyes on it.

## What is this, exactly?

CFA (Cloud File Archive — I needed a name for the header) is the format
MediaBridge writes when it backs a library up to a GCS bucket. It's
deliberately boring at the top level:

- Every file gets hashed (SHA-256) before it goes anywhere.
- Files get packed into plain POSIX tar archives — small files get
  clumped together, oversized files get split into parts, everything
  else gets its own archive.
- Every archive gets a companion JSON index describing what's inside it.
- Nothing is ever deleted or overwritten. New data always lands under a
  fresh ID.

If that's all you need, you can stop reading the spec after section 7.
Sections 8 through 10 cover the optional stuff — client-side encryption,
compression, and per-archive storage tiers — each of which you can ignore
entirely and still have a conformant, working backup.

## Why write a spec at all?

Two reasons, honestly. The practical one: I want to be able to restore a
MediaBridge backup with a completely different tool someday — `tar` and a
JSON parser, if I have to — without needing MediaBridge's database or even
MediaBridge itself. Writing the format down as a spec, not just as
whatever `packer.py` does this week, is what makes that plausible.

The other reason is that the code and the internal design notes had
quietly drifted apart. I had a `docs/cfa-spec.md` sitting around from
earlier in the project, but by the time encryption, compression, and
storage tiers all landed, it was describing a system that didn't quite
exist anymore — there's a `DEVIATIONS.md` file in the repo that's
basically a running list of "the spec says X, the code actually does Y,
here's why." Useful for me mid-project, useless as a public document.
Nobody should have to cross-reference two files to know what's actually
happening.

So: this is a rewrite, not an update. It folds all of that drift back in
and is meant to stand alone. I'm calling it v1.0 because — despite an
earlier draft floating around internally as "v2.0" — nothing has actually
been published before now. This is the first version anyone outside my
own repo has seen.

## The one thing that'll bite you if you don't know it

If you only take one thing away: **no archive object is allowed to exceed
`max_size`, but tar format overhead means you can't just pack `max_size`
bytes of payload and expect that to hold.** A PAX header, block padding,
end-of-archive padding — it adds up to a measured ~13 KiB worst case on a
file with a long path. So the actual packing ceiling is `max_size − 1
MiB`, and that same margin governs three separate decisions: where the
single/part boundary sits, how big a split chunk is, and where a clump
gets sealed. Get this wrong and you'll ship archives that are
technically over your own stated limit, which is exactly what happened in
an earlier draft before I caught it.

It's a small thing, but it's the kind of small thing that's very easy to
get subtly wrong in an independent implementation, so I spelled it out
explicitly rather than leaving it as an exercise.

## The encryption bit I'm least sure about

Section 8 covers optional per-file AES-256-GCM encryption. The part I
expect pushback on: each file's encryption key is *derived deterministically*
from a master key plus that file's own SHA-256. No separate key store,
no per-file metadata to keep in sync — just the passphrase and the hash
you already have cataloged.

The tradeoff this buys is real: two files with identical content always
derive the same key. I'm treating that as acceptable for this format (a
private bucket is the assumed confidentiality boundary, and every
encryption still uses a fresh random nonce, so GCM's actual safety
property — nonce uniqueness per key — isn't violated). But I know "always
derives the same key for the same content" is a sentence that makes
security people twitch, and I'd genuinely like someone who does more of
that work than me to tell me if I'm fine or if I'm fooling myself.

## What I deliberately left out

The old internal draft implied you could restore a file by scanning
index files in the bucket directly, with no database involved — a real
disaster-recovery feature if your metadata store is the thing that's
gone. It was never actually built. Rather than publish a spec that
describes an aspirational feature as if it works, I moved it to an
explicit "Out of Scope" section and said why: searching for a hash across
an unbounded number of index files with no defined cost bound isn't a
small addition, it needs its own design. If enough people want it, I'll
scope it properly later — but I'd rather under-promise here than have
someone build against a restore path that doesn't exist.

Also out of scope, on purpose: version history, deleting old backups,
compaction, anything Windows-specific, and any storage provider besides
GCS. Not because they're uninteresting, just because none of them are
solved by this document.

## What I'd actually like feedback on

- **The encryption key derivation** (above) — tell me if the tradeoff is
  reasonable or if I'm underselling the risk.
- **The object layout** (section 4) — archives write as a same-directory
  `<id>.tar` / `<id>.json` pair now, but earlier versions used a separate
  `archives/` / `index/` folder split, and the spec says both are
  permanently valid so nothing already written has to be migrated. Is
  that a reasonable thing to bless indefinitely, or should there be an
  expiration date on supporting the old layout?
- **Whether "spec" is even the right container for this.** It's about
  100 lines longer than I'd like, and I go back and forth on whether the
  encryption/compression sections should be split into their own
  documents that this one references, rather than all living in one file.

If you build backup tooling, or you've written a format spec that's held
up (or hasn't) over time, I'd really like to hear about it. Comments open
below, or find me wherever SteveOmics.com says to find me.
